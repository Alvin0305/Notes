    CoAP Packet Structure

    +--------------------------------------+
| Version | Type | TKL                 |
+--------------------------------------+
| Code                                 |
+--------------------------------------+
| Message ID (16 bits)                 |
+--------------------------------------+
| Token (0-8 bytes)                    |
+--------------------------------------+
| Options (0 or more)                  |
+--------------------------------------+
| Payload (optional)                   |
+--------------------------------------+

    2.1 Version (2 bits)¶

    Identifies the CoAP protocol version.

    Currently, the standardized CoAP version is:

    Version = 1

    It occupies the first two bits of the first byte.

    2.2 Type (2 bits)¶

    Specifies the message type.

    CoAP defines four message types:

    Type Value Meaning
    CON 0 Confirmable
    NON 1 Non-confirmable
    ACK 2 Acknowledgement
    RST 3 Reset

    These are important because they determine how CoAP handles message delivery.

    CON — Confirmable¶

    A confirmable message requires acknowledgement.

    Suppose a PLC receives a command to activate a critical actuator.

    The sender wants to know whether the message was successfully received.

    It sends:

    Client → Server: CON POST /command

    The receiver responds:

    Server → Client: ACK

    If the sender doesn't receive an acknowledgement within the retransmission timeout, it can retransmit the message.

    NON — Non-confirmable¶

    A non-confirmable message does not require an acknowledgement.

    Useful for frequently transmitted sensor measurements where occasional packet loss is acceptable.

    For example:

    Sensor → PLC: NON POST /temperature

    If one temperature reading gets lost, the next reading may arrive shortly afterward.

    ACK — Acknowledgement¶

    Indicates that a confirmable message was received.

    An ACK can be:

    • An empty ACK, which acknowledges receipt but does not contain the response.
    • A piggybacked ACK, which acknowledges the request and carries the response in the same message.

    Your implementation uses the second approach.

    RST — Reset¶

    Indicates that a message was received but could not be processed or associated with the expected communication context.

    For example, a device might receive a message with an unknown Message ID and respond with RST.

    2.3 Token Length (4 bits)¶

    Abbreviated as TKL.

    Specifies the length of the Token field.

    Valid values:

    0 to 8 bytes

    Why do we need a token?

    The Message ID and Token serve different purposes.

    • Message ID: Identifies a CoAP message for message-layer reliability and duplicate detection. Each message will be having a new message id. It will be sequential
    • Token: Correlates a response with the corresponding request. Is for identifying which response map to which request. A request and response will have the same token. Token of request is chosen randomly.

    2 cases: - Client or server is free: Might send piggy backed response which will contain type = ACK and the response payload also. In this case, message id will be the same - Client or server is busy: Might send a empty ACK so that other guy will not re-transmit. In this case, the message id will be different

    For example:

    Request:
Message ID = 100
Token      = 0x12 0x34

Response:
Message ID = 100
Token      = 0x12 0x34

    For a piggybacked ACK, the Message ID is copied from the request.

    For a separate response, the response has its own Message ID, but retains the original request's Token.

    This distinction is important.

    2.4 Code (8 bits)¶

    Specifies the request method or response status.

    It is divided into three bits for the class and five bits for the detail.

    The general representation is:

    Class.Detail

    Request codes¶

    Method Code Meaning
    GET 0.01 Retrieve a resource
    POST 0.02 Create a resource or process submitted data
    PUT 0.03 Update or create a resource
    DELETE 0.04 Delete a resource

    For example:

    0.02 = POST

    Your implementation uses POST.

    Response codes¶

    Some commonly used response codes:

    Code Meaning
    2.01 Created
    2.02 Deleted
    2.04 Changed
    2.05 Content
    4.00 Bad Request
    4.01 Unauthorized
    4.03 Forbidden
    4.04 Not Found
    5.00 Internal Server Error

    An interesting detail for your project:

    Your earlier implementation uses response code 131.

    In hexadecimal:

    131 decimal = 0x83

    Breaking it down:

    10000011

    Class = 100 = 4

    Detail = 00011 = 3

    Therefore:

    4.03 = Forbidden

    This is appropriate when your PLC rejects an unauthorized command.

    2.5 Message ID (16 bits)¶

    The Message ID is a 16-bit identifier.

    Its range is:

    0 to 65535

    It serves two major purposes:

    1. Detecting duplicate messages.
    2. Matching acknowledgements with confirmable messages.

    For example:

    Request:
Message ID = 500

ACK:
Message ID = 500

    If a confirmable request is retransmitted because its ACK was lost, the receiver can recognize the duplicate using the Message ID.

    Note that Message IDs are scoped to the message-layer communication between endpoints and are not globally unique identifiers.

    2.6 Token (0–8 bytes)¶

    As explained earlier, the Token correlates requests and responses.

    Unlike the Message ID, it belongs to the request-response interaction.

    For example:

    Request:
Token = AB CD

Response:
Token = AB CD

    A server can use the token to identify which request a response belongs to.

    Your implementation generates a two-byte token from the Message ID. That is a convenient choice for your simulation, although a production implementation should generate tokens with appropriate uniqueness.

    2.7 Options¶

    Options provide additional metadata about a CoAP message.

    Examples include:

    Option Option Number Purpose
    If-Match 1 Conditional request
    Uri-Host 3 Host identification
    ETag 4 Resource version identification
    If-None-Match 5 Conditional request
    Observe 6 Resource observation
    Uri-Port 7 Port information
    Location-Path 8 Resource location
    Uri-Path 11 Resource path
    Content-Format 12 Payload format
    Max-Age 14 Response freshness
    Uri-Query 15 Query parameters
    Accept 17 Accepted response format
    Block2 23 Block-wise transfer
    Block1 27 Block-wise transfer

    Your implementation currently supports only the URI-Path option.

    How are options encoded?¶

    This is an interesting part of CoAP.

    Each option has:

    +-------------------+
| Delta | Length    |
+-------------------+
| Option Value      |
+-------------------+

    Both Delta and Length are four bits.

    Delta is the difference between the current option number and the previous option number.

    Length specifies the number of bytes in the option value.

    Why Delta instead of storing the complete option number?

    Because CoAP options are ordered by option number. Delta encoding reduces the number of bits required.

    For the first option:

    Previous option number = 0
Current option number  = 11 (URI-Path)

Delta = 11 - 0 = 11

    Suppose the URI path is:

    /temperature

    The option header is:

    Delta  = 11
Length = 11

    Assuming the path segment is temperature, which has 11 characters:

    Option Header = 1011 1011
              = 0xBB

    The complete option becomes:

    BB 74 65 6D 70 65 72 61 74 75 72 65

    Here:

    • BB is the option header.
    • Remaining bytes represent temperature in ASCII.

    One subtlety: URI-Path is a repeatable option. A path such as /sensor/temperature is encoded using two URI-Path options, one for sensor and another for temperature.

    2.8 Payload¶

    The payload contains the actual application data.

    For example:

    POST /temperature

Payload: 75

    The payload is optional.

    CoAP uses a special byte:

    0xFF

    to indicate the beginning of the payload.

    Therefore:

    Options
0xFF
Payload

    If the message has no payload, the payload marker must not be included.
