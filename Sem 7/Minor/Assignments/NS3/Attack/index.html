    IIoT CoAP Simulation — Complete Technical Explanation¶

    This is the most important part of your assignment from a security perspective. Your Coap.cc explained how the protocol works internally. Now, the Attacker, main.cpp, and Constants.h show how you use that protocol to create an industrial control system and simulate attacks against it.

    I want to approach this as if we're preparing you to explain the entire project to your faculty.

    We'll cover:

    1. Overall architecture and how the simulation works.
    2. How ns-3 constructs the network.
    3. How the Sensor, PLC, and Cooler communicate using CoAP.
    4. How your Attacker application works internally.
    5. All three attacks implemented in your code.
    6. How packet sniffing and IP spoofing work.
    7. HMAC authentication and replay protection.
    8. The relationship between your attacks and STUXNET.
    9. Security threats, defenses, and limitations.
    10. Likely viva questions.

    1. Understanding the overall project¶

    First, let's understand what you're actually simulating.

    Your assignment asks you to construct an Industrial Internet of Things (IIoT) environment using ns-3 and investigate security threats against a PLC-based industrial control system.

    Your simulation contains four devices:

    Device IP address Responsibility
    Temperature Sensor 10.1.1.1 Measures temperature and sends readings
    PLC 10.1.1.2 Processes sensor readings and controls the actuator
    Cooler 10.1.1.3 Executes ON/OFF commands
    Attacker 10.1.1.4 Observes communication and attempts attacks

    The architecture looks like this:

    Conceptually:

                        IIoT NETWORK
                  10.1.1.0/24

    +----------------+ 
    | Temperature    |
    | Sensor         |
    | 10.1.1.1       |
    +----------------+
            |
            | CoAP / UDP
            |
            v
    +----------------+
    | PLC            |
    | 10.1.1.2       |
    |                |
    | Control Logic  |
    +----------------+
            |
            | CoAP / UDP
            |
            v
    +----------------+
    | Cooler         |
    | 10.1.1.3       |
    |                |
    | Actuator       |
    +----------------+


    +----------------+
    | Attacker       |
    | 10.1.1.4       |
    |                |
    | Sniffing       |
    | Spoofing       |
    | Replay         |
    +----------------+

    An important detail: All four devices are connected to the same LAN.

    This makes it possible for the attacker to observe traffic exchanged between the PLC and Cooler.

    1.1 What is the normal operation?¶

    Suppose the temperature threshold is 70°C.

    Your PLC is configured with:

    plcApp->SetThreshold(70.0);

    The sensor periodically measures temperature.

    Let's assume it measures 75°C.

    The communication happens as follows:

    Step 1: Sensor sends the temperature to the PLC.

    POST /temperature

Payload: 75

    Step 2: PLC receives the temperature.

    It compares:

    Measured temperature = 75°C
Threshold             = 70°C

    Since:

    75 > 70

    The PLC decides that cooling is necessary.

    Step 3: PLC sends a command to the cooler.

    POST /command

Payload: COOLER ON

    Step 4: Cooler receives the command and activates itself.

    Step 5: Cooler sends a response to the PLC indicating whether the command was accepted.

    This is the normal industrial control loop.

    The attacker attempts to interfere with this communication.

    2. Understanding main.cpp — How the simulation is constructed¶

    Your main.cpp is responsible for creating the entire network and scheduling the applications.

    Let's go through it.

    2.1 Configuration loading¶

    ConfigParser parser;
IIoTConfig config = parser.parse("config.no-hmac-defense.json");

    You have a configuration file that controls which attacks and defenses are enabled.

    Instead of hardcoding attack behavior into the attacker, you load configuration parameters.

    For example, the configuration might contain:

    {
  "do-direct-command-injection": false,
  "send-spoofed-packet": true,
  "send-invalid-hmac": true,
  "send-replay-attack": true,
  "defend-direct-command-injection": true,
  "defend-ip-spoofing": true,
  "defend-replay-attack": true
}

    The parser converts these JSON values into an IIoTConfig object.

    The applications use this object to determine their behavior.

    This allows you to execute different attack-defense combinations without recompiling your program.

    2.2 Creating nodes¶

    NodeContainer nodes;
nodes.Create(4);

    This creates four ns-3 nodes.

    A node represents a networked device in the simulation.

    It is not necessarily a physical computer.

    In your project, each node represents one industrial device.

    You retrieve them using:

    Ptr<Node> sensor = nodes.Get(0);
Ptr<Node> plc = nodes.Get(1);
Ptr<Node> cooler = nodes.Get(2);
Ptr<Node> attacker = nodes.Get(3);

    The order is important because it determines which node receives which IP address later.

    2.3 Installing the Internet stack¶

    InternetStackHelper internet;
internet.Install(nodes);

    What does this do?

    An ns-3 Node doesn't automatically have a complete network protocol stack.

    The InternetStackHelper installs the necessary networking components.

    These include:

    • IPv4.
    • UDP.
    • TCP.
    • Routing-related functionality.
    • Socket interfaces.

    This allows your applications to communicate using IP and UDP.

    Remember the networking hierarchy:

    Application Layer      CoAP
        |
Transport Layer        UDP
        |
Network Layer          IPv4
        |
Data Link Layer        CSMA/Ethernet
        |
Physical Layer         Simulated link

    Your CoAP implementation operates at the application layer.

    ns-3 provides the lower networking layers.

    2.4 Creating the LAN using CSMA¶

    CsmaHelper csma;

csma.SetChannelAttribute(
    "DataRate",
    StringValue("100Mbps")
);

csma.SetChannelAttribute(
    "Delay",
    TimeValue(MicroSeconds(10))
);

NetDeviceContainer devices = csma.Install(nodes);

    This is particularly important.

    You're using CSMA (Carrier Sense Multiple Access) to connect the four nodes.

    CSMA is a channel-access mechanism where devices listen to the medium before transmitting.

    In ns-3, CsmaHelper creates a shared broadcast LAN-like network.

    Your configuration specifies:

    Parameter Value
    Data rate 100 Mbps
    Channel delay 10 microseconds
    Number of devices 4

    What does 100 Mbps mean?

    The simulated channel can transmit at a configured data rate of 100 megabits per second.

    What does 10 microseconds mean?

    It specifies the propagation delay configured for the CSMA channel.

    Why CSMA is important for your attacker¶

    All four devices share the same simulated LAN.

    When the PLC sends a packet to the Cooler, the attacker can receive a promiscuous copy of that packet through the shared channel.

    This is how your packet-sniffing mechanism works.

    One important clarification:

    A CSMA LAN in ns-3 is not a simulation of a modern switched Ethernet network with realistic switch port isolation and all its security features. Your setup deliberately creates an environment where passive observation is possible.

    2.5 Assigning IP addresses¶

    Ipv4AddressHelper address;

address.SetBase(
    "10.1.1.0",
    "255.255.255.0"
);

Ipv4InterfaceContainer interfaces =
    address.Assign(devices);

    This assigns IPv4 addresses to the four devices.

    Because the devices were installed in this order:

    0 → Sensor
1 → PLC
2 → Cooler
3 → Attacker

    The addresses become:

    Sensor   = 10.1.1.1
PLC      = 10.1.1.2
Cooler   = 10.1.1.3
Attacker = 10.1.1.4

    The subnet mask is:

    255.255.255.0

    Which means:

    Network = 10.1.1.0/24

    All four devices are on the same subnet.

    Therefore, they can communicate directly without needing a router.

    3. Understanding the application lifecycle¶

    After constructing the network, you attach applications to individual nodes.

    ns-3 applications generally have two important lifecycle methods:

    StartApplication()
StopApplication()

    StartApplication() is called when the application starts.

    StopApplication() is called when the application stops.

    Let's examine your scheduling.

    Application Start Stop
    Sensor 1.0 s 5.0 s
    PLC 0.0 s 5.5 s
    Cooler 0.0 s 5.5 s
    Attacker 0.0 s 5.0 s

    Why does the PLC start at 0 seconds?

    Because it should be ready to receive sensor messages as soon as the sensor begins transmitting.

    The attacker also starts at 0 seconds so it can begin sniffing before the other devices start communicating.

    3.1 Capturing network packets¶

    csma.EnablePcapAll("iiot-coap", true);

    This enables packet capture for all network devices.

    It generates PCAP files that can be opened using Wireshark.

    You can inspect:

    • Source IP.
    • Destination IP.
    • UDP source port.
    • UDP destination port.
    • CoAP payload.
    • Message IDs.
    • Packet retransmissions, if implemented.

    This is extremely useful for demonstrating your project.

    3.2 Running the simulation¶

    Simulator::Stop(Seconds(6.0));

Simulator::Run();
Simulator::Destroy();

    Simulator::Run() executes all scheduled events.

    The simulation stops at six seconds.

    Simulator::Destroy() cleans up the simulator state after execution.

    One thing to understand about ns-3:

    Simulation time is not the same as real-world execution time.

    The simulator advances through scheduled events rather than waiting for six actual seconds.

    4. Understanding Constants.h¶

    Your constants file centralizes the values used by multiple components.

    constexpr char sensorIP[] = "10.1.1.1";
constexpr char plcIP[] = "10.1.1.2";
constexpr char coolerIP[] = "10.1.1.3";
constexpr char attackerIP[] = "10.1.1.4";

    These represent the expected device addresses.

    Then:

    constexpr char commandString[] = "command";

    This represents the CoAP resource:

    /command

    Your commands are:

    constexpr char coolerOffCommand[] = "COOLER OFF";
constexpr char coolerOnCommand[] = "COOLER ON";

    These are application-level command strings.

    The attacker attempts to inject COOLER OFF because turning off the cooling system when the temperature is high can be dangerous.

    Next:

    constexpr unsigned int attackerPort = 49152;

    This is the UDP source port used by your attacker's raw-packet construction.

    The destination port is:

    Coap::PORT

    Which should be 5683 in your CoAP implementation.

    Finally:

    namespace protocol {
    constexpr unsigned int udp = 17;
};

    Why 17?

    Because the IPv4 Protocol field uses the value:

    17 = UDP

    For reference:

    Protocol IPv4 Protocol Number
    ICMP 1
    TCP 6
    UDP 17

    This is how the attacker identifies UDP packets when inspecting IP headers.

    5. Understanding the Attacker application¶

    Now we reach the most interesting part.

    Your attacker implements four important capabilities:

    1. Passive packet sniffing.
    2. Direct command injection.
    3. IP spoofing.
    4. Replay attacks.

    It also performs an invalid-HMAC attack.

    Let's first understand the overall design.

    5.1 Attacker's internal architecture¶

                     ATTACKER
                     |
          +----------+----------+
          |                     |
          v                     v
    UDP Socket             Promiscuous
    (Responses)            Packet Capture
          |                     |
          |                     |
          v                     v
    HandleRead()          PromiscSniffer()
                                |
                                v
                        Capture valid PLC
                        command packet
                                |
                                v
                         Store raw bytes
                                |
                                v
                         Replay attack

    The attacker has two different communication mechanisms:

    Normal UDP socket:

    Used to send ordinary UDP packets and receive responses.

    Raw IPv4 socket:

    Used to construct packets with a forged source IP address.

    This distinction is central to understanding your implementation.

    6. Attacker initialization — StartApplication()¶

    Let's examine the first important function.

    void Attacker::StartApplication() {
    socket = Socket::CreateSocket(
        GetNode(),
        UdpSocketFactory::GetTypeId()
    );

    socket->Bind();

    socket->SetRecvCallback(
        MakeCallback(&Attacker::HandleRead, this)
    );

    6.1 Creating a UDP socket¶

    Socket::CreateSocket(
    GetNode(),
    UdpSocketFactory::GetTypeId()
);

    This creates a UDP socket belonging to the attacker node.

    The socket is used for normal UDP communication.

    Next:

    socket->Bind();

    This binds the socket to a local endpoint.

    Since no explicit address or port is provided, ns-3 selects an available local port.

    Then:

    socket->SetRecvCallback(
    MakeCallback(&Attacker::HandleRead, this)
);

    This registers a callback.

    Whenever data arrives at this socket, ns-3 invokes:

    Attacker::HandleRead()

    This is an event-driven programming model.

    The attacker doesn't need to continuously check whether a packet has arrived.

    ns-3 invokes the callback when the socket becomes readable.

    6.2 Enabling promiscuous packet capture¶

    for (uint32_t i = 0;
     i < GetNode()->GetNDevices();
     i++) {

    GetNode()->GetDevice(i)->SetPromiscReceiveCallback(
        MakeCallback(&Attacker::PromiscSniffer, this)
    );
}

    This is one of the most important pieces of your attacker implementation.

    What is promiscuous mode?¶

    Normally, a network interface processes packets intended for it.

    For example:

    Source:      PLC
Destination: Cooler

    The attacker is neither the source nor destination.

    Normally, the attacker wouldn't receive this packet through its ordinary UDP socket.

    Promiscuous mode allows the network device to receive copies of packets that are not addressed to it.

    This is useful for network monitoring and packet sniffing.

    In your simulation, the attacker registers a promiscuous receive callback on each of its network devices.

    Whenever a suitable packet is visible to the device, ns-3 invokes:

    PromiscSniffer()

    Notice that promiscuous mode doesn't mean the attacker can magically observe every packet on every network.

    It depends on the network topology and underlying device/channel behavior.

    Your shared CSMA LAN makes this possible.

    ATTACKER_LOG_INFO(
    "Promiscous packet capture enabled"
);

    This simply logs that the packet capture mechanism has been enabled.

    6.3 Scheduling attacks¶

    Simulator::Schedule(
    Seconds(2.5),
    &Attacker::SendConfiguredAttacks,
    this
);

    This schedules the configured attacks at simulation time 2.5 seconds.

    Then:

    if (config.sendReplayAttack) {
    Simulator::Schedule(
        Seconds(4.5),
        &Attacker::SendReplayAttack,
        this
    );
}

    The replay attack is scheduled separately at 4.5 seconds.

    Why separate them?

    Because a replay attack requires an already captured legitimate command.

    Your attacker first needs to observe legitimate PLC-to-Cooler communication.

    Only then can it replay that captured packet.

    The timing is therefore:

    0.0 s  Attacker starts
       |
       v
       Enables promiscuous capture
       |
1.0 s  Sensor starts
       |
       v
       Normal sensor/PLC communication
       |
       v
       PLC sends command to Cooler
       |
       v
       Attacker captures command
       |
2.5 s  Configured attacks execute
       |
       v
4.5 s  Replay attack executes
       |
5.0 s  Attacker stops

    The exact availability of a captured command at 4.5 seconds depends on your sensor readings and PLC behavior. Your code explicitly checks for that before replaying.

    7. Understanding packet sniffing — PromiscSniffer()¶

    This function is worth understanding in considerable detail because it combines networking concepts from multiple layers.

    bool Attacker::PromiscSniffer(
    Ptr<NetDevice> device,
    Ptr<const Packet> packet,
    uint16_t protocol,
    const Address& from,
    const Address& to,
    NetDevice::PacketType packetType
)

    This callback is invoked when the network device receives a packet in promiscuous mode.

    Let's understand its parameters.

    Parameter Meaning
    device Network device that received the packet
    packet Received packet
    protocol EtherType identifying the network-layer protocol
    from Source link-layer address
    to Destination link-layer address
    packetType Classification of the received packet

    Step 1: Identify IPv4 packets¶

    if (protocol != 0x0800) {
    return false;
}

    What is 0x0800?

    It is the Ethernet EtherType for IPv4.

    Some common EtherTypes:

    EtherType Protocol
    0x0800 IPv4
    0x0806 ARP
    0x86DD IPv6

    Your attacker only wants to inspect IPv4 packets.

    Therefore, it ignores other protocols.

    Step 2: Copy the packet¶

    Ptr<Packet> copy = packet->Copy();

    Why copy it?

    Because the attacker is inspecting the packet.

    The original packet belongs to ns-3's packet-processing mechanism.

    Modifying it could interfere with normal packet processing.

    Therefore, it creates a copy and removes headers from that copy.

    This is an important concept when working with packet inspection.

    Step 3: Extract the IPv4 header¶

    Ipv4Header ip;

if (copy->RemoveHeader(ip) == 0) {
    return false;
}

    An IPv4 packet has a header followed by its payload.

    Conceptually:

    +-------------------------+
| IPv4 Header             |
+-------------------------+
| Transport Layer Header  |
+-------------------------+
| Application Data        |
+-------------------------+

    RemoveHeader() extracts the IPv4 header and removes it from the copied packet.

    Now copy starts with the IPv4 payload.

    The extracted header is stored in:

    Ipv4Header ip;

    This allows you to inspect fields such as:

    • Source IP.
    • Destination IP.
    • Protocol number.
    • TTL.
    • Identification.
    • Total packet size.

    Step 4: Filter the source and destination¶

    if (
    ip.GetSource() != Ipv4Address(constants::plcIP) ||
    ip.GetDestination() != Ipv4Address(constants::coolerIP) ||
    ip.GetProtocol() != constants::protocol::udp
) {
    return false;
}

    This is where your attacker becomes selective.

    It only wants packets satisfying:

    Source IP      = 10.1.1.2 (PLC)
Destination IP = 10.1.1.3 (Cooler)
Protocol       = UDP

    Why these conditions?

    Because the attacker wants to capture commands sent by the PLC to the Cooler.

    It doesn't need sensor-to-PLC traffic for this particular replay attack.

    It also doesn't need unrelated network traffic.

    This is called packet filtering.

    Step 5: Extract the UDP header¶

    UdpHeader udp;

if (copy->RemoveHeader(udp) == 0) {
    return false;
}

    After removing the IPv4 header, the packet begins with the UDP header.

    A UDP header contains:

    Field Size
    Source Port 16 bits
    Destination Port 16 bits
    Length 16 bits
    Checksum 16 bits

    Total:

    8 bytes

    Your attacker extracts this header so it can inspect the destination port.

    Step 6: Check the CoAP port¶

    if (udp.GetDestinationPort() != Coap::PORT) {
    return false;
}

    CoAP over UDP normally uses port:

    5683

    Your attacker only wants CoAP traffic.

    Therefore, it ignores UDP packets sent to other ports.

    At this point, it has established:

    IPv4 packet
    |
    v
Source = PLC
Destination = Cooler
    |
    v
UDP packet
    |
    v
Destination port = 5683
    |
    v
Potential CoAP packet

    Step 7: Extract the CoAP bytes¶

    std::vector<uint8_t> bytes(copy->GetSize());

if (bytes.empty()) {
    return false;
}

copy->CopyData(
    bytes.data(),
    static_cast<uint32_t>(bytes.size())
);

    The IPv4 and UDP headers have been removed.

    What remains is the UDP payload.

    In your application, the UDP payload contains the CoAP message.

    Therefore, you copy it into a byte vector.

    Step 8: Decode the CoAP packet¶

    Coap::Message message;

if (!Coap::Decode(
        bytes.data(),
        bytes.size(),
        message
    )) {
    return false;
}

    You reuse your earlier CoAP decoder.

    This is a nice separation of responsibilities.

    The sniffer doesn't need to know how CoAP headers, tokens, options, and payloads are encoded.

    It delegates that work to:

    Coap::Decode()

    The resulting object contains the decoded fields.

    Step 9: Check the CoAP message¶

    if (
    message.type != Coap::CON ||
    message.code != Coap::POST ||
    message.path != constants::commandString
) {
    return false;
}

    The attacker only captures messages satisfying:

    Type = CON
Method = POST
Path = /command

    Why?

    Because these are the messages that represent confirmable commands sent to the Cooler.

    Notice that your attacker doesn't capture every CoAP message.

    It specifically targets control commands.

    Step 10: Check the payload structure¶

    const size_t first =
    message.payload.find('|');

const size_t second =
    first == std::string::npos
        ? std::string::npos

    13.1 What is a replay attack?¶

    A replay attack occurs when an attacker captures a legitimate message and retransmits it later.

    PLC → Cooler

    • HMAC.
    • Sequence number.

    This is the replay attack.

    Now suppose an attacker replays the original command:

    COOLER ON|51|VALID_HMAC

    The Cooler checks:

    51 > 51

    False.

    It rejects the message.

    What happens when all three defenses are enabled?¶

    Consider these attacks:

    Attack IP validation HMAC Replay protection Expected result
    Direct injection Reject Not reached Not reached Rejected
    Spoofed command without HMAC Pass Reject Not reached Rejected
    Invalid HMAC with spoofed IP Pass Reject Not reached Rejected
    Replay of valid command Pass Pass Reject Rejected
    Legitimate PLC command Pass Pass Pass Accepted

    This is the security model your assignment is trying to demonstrate.

    The important takeaway is:

    Multiple independent security mechanisms are needed because each one protects against a different class of attack.

    18. Other security threats in an IIoT environment¶

    Your assignment asks you to threat-model the system and list potential security threats.

    Your implemented attacks are a good starting point, but you should know the broader threat landscape.

    Let's classify the threats.

    18.1 Threats against confidentiality¶

    Confidentiality means preventing unauthorized parties from reading information.

    Packet sniffing¶

    An attacker monitors communication between the sensor, PLC, and actuator.

    If communication is unencrypted, the attacker might observe:

    • Temperature measurements.
    • Industrial commands.
    • Device addresses.
    • Communication patterns.
    • Authentication metadata.

    Your PromiscSniffer() demonstrates this type of threat.

    Information disclosure¶

    An attacker might obtain:

    • HMAC-related information.
    • Configuration details.
    • Device identifiers.
    • Operational parameters.

    Note that an HMAC is not the secret key itself, but repeated exposure of application data can still reveal sensitive operational information.

    Possible defense: DTLS or OSCORE, along with proper key management.

    18.2 Threats against integrity¶

    Integrity means preventing unauthorized modification of data.

    Packet modification¶

    An attacker intercepts:

    COOLER ON

    and attempts to change it to:

    COOLER OFF

    Without message integrity protection, the receiver might accept the modified message.

    Your HMAC mechanism addresses this threat.

    Sensor data manipulation¶

    An attacker modifies:

    Temperature = 75°C

    to:

    Temperature = 25°C

    The PLC might incorrectly conclude that cooling is unnecessary.

    This is particularly dangerous because the PLC could be operating normally based on false input.

    Unauthorized PLC programming¶

    An attacker modifies the PLC's control logic.

    This is conceptually closer to the control-logic manipulation aspect of STUXNET.

    Your current implementation doesn't simulate PLC firmware or program modification, but it is an important threat to mention.

    18.3 Threats against availability¶

    Availability means ensuring that the industrial system remains operational.

    Denial of Service (DoS)¶

    An attacker floods the PLC with a large number of requests.

    For example:

    Attacker → PLC

POST /temperature
POST /temperature
POST /temperature
POST /temperature
...

    The PLC may spend excessive processing resources handling malicious requests.

    UDP flooding¶

    Since your application uses UDP, an attacker could send large volumes of UDP datagrams to the CoAP port.

    This could cause:

    • CPU exhaustion.
    • Increased packet-processing overhead.
    • Application-level resource exhaustion.
    • Legitimate messages being delayed or dropped.

    Resource exhaustion¶

    An attacker may attempt to exhaust:

    • Memory.
    • Socket buffers.
    • Packet queues.
    • Application processing capacity.

    Possible defenses include rate limiting, traffic filtering, request validation, and resource limits.

    19. Important networking concepts your faculty might ask about¶

    Since your project uses ns-3, UDP, IPv4, raw sockets, and CSMA, I would prepare these concepts too.

    19.1 What is the difference between a normal UDP socket and a raw socket?¶

    Normal UDP socket Raw IPv4 socket
    Application sends UDP data Application can work with IP packets
    OS/network stack constructs IP header Can supply a custom IP header
    Usually cannot arbitrarily forge source IP Can construct packets with a forged source IP
    Easier to use More control over packet construction

    Your implementation uses both.

    Normal UDP socket:

    Socket::CreateSocket(
    GetNode(),
    UdpSocketFactory::GetTypeId()
);

    Raw IPv4 socket:

    Socket::CreateSocket(
    GetNode(),
    Ipv4RawSocketFactory::GetTypeId()
);

    19.2 What is promiscuous mode?¶

    Normally, a network interface accepts packets according to its normal reception rules.

    In promiscuous mode, the interface can deliver packets not addressed to its own MAC address to the packet-capture mechanism.

    This is commonly used by:

    • Wireshark.
    • Network intrusion detection systems.
    • Network monitoring tools.
    • Packet analyzers.

    Your attacker uses this functionality to observe PLC-to-Cooler communication.

    19.3 What is the difference between IP and MAC addresses?¶

    IP address MAC address
    Network-layer address Data-link-layer address
    Used for IP communication Used for local link delivery
    IPv4 is 32 bits Ethernet MAC is normally 48 bits
    Can change between networks Usually associated with a network interface

    Your IP spoofing attack modifies the IPv4 source address.

    It doesn't necessarily modify the Ethernet source MAC address.

    Therefore, IP spoofing and MAC spoofing are different attacks.

    19.4 What is the UDP checksum?¶

    UDP has a 16-bit checksum used to detect corruption.

    It covers the UDP header, UDP data, and an IP pseudo-header.

    Your code:

    udp.EnableChecksums();

udp.InitializeChecksum(
    forgedSource,
    destination,
    constants::protocol::udp
);

    calculates the checksum using the forged source and destination addresses.

    This is necessary because the pseudo-header contains those IP addresses.

    A checksum is not authentication.

    An attacker who can construct a packet can also calculate a valid checksum.

    This is why the UDP checksum cannot replace HMAC.

    19.5 What is the difference between IPv4 Identification and CoAP Message ID?¶

    This is a particularly good viva question because your code uses the same variable for both.

    ip.SetIdentification(mid);

    The IPv4 Identification field is used for IP fragmentation and reassembly.

    Meanwhile:

    CoAP Message ID

    is used for CoAP duplicate detection and matching acknowledgements.

    They are entirely separate fields.

    The fact that you assign them the same number is just an implementation choice.

    20. Important implementation limitations and things to watch¶

    There are a few details in your code that are worth understanding before your viva.

    These aren't necessarily bugs, but they define what your simulation actually demonstrates.

    20.1 Your attacker doesn't verify HMACs¶

    In PromiscSniffer():

    message.payload.size() - second - 1 != 64

    You only check whether the payload has the expected structure.

    You don't calculate or verify the HMAC.

    That's intentional for your replay attack: the attacker captures an already authenticated message and reuses it.

    20.2 Replay attack preserves the original CoAP Message ID¶

    Your replay attack retransmits the original CoAP bytes.

    Therefore, it preserves:

    • Original Message ID.
    • Original Token.
    • Original command.
    • Original sequence number.
    • Original HMAC.

    This lets you demonstrate why application-level replay protection is necessary.

    However, a complete CoAP implementation should also maintain duplicate-detection state for Confirmable messages. Your current Coap.cc doesn't implement that mechanism.

    20.3 CoAP reliability isn't fully implemented¶

    Your code supports CON and ACK message types.

    But it doesn't implement:

    • Retransmission timers.
    • Exponential backoff.
    • Duplicate detection.
    • Separate responses.
    • Complete message-exchange state management.

    So your implementation supports the basic CoAP message format and request-response exchange, not the entire CoAP standard.

    20.4 Your application uses a custom HMAC payload format¶

    This:

    COMMAND|SEQUENCE|HMAC

    is your application's own message format.

    It isn't a mandatory CoAP structure.

    CoAP simply transports this payload.

    You could use JSON, CBOR, or another application-level representation instead.

    20.5 IP spoofing doesn't mean the attacker receives the response¶

    As discussed earlier, when the attacker forges:

    Source IP = PLC

    the Cooler sends its response to the PLC's IP address.

    The attacker won't normally receive that response through its ordinary UDP socket.

    This is expected behavior.

    20.6 Your replay defense must check freshness, not just HMAC¶

    A replayed message can have:

    • Correct source IP.
    • Valid HMAC.
    • Correct CoAP structure.
    • Previously accepted command.

    Only a freshness mechanism can distinguish the old message from a new one.

    Your sequence number is intended to solve this.

    20.7 Your HMAC should cover all security-relevant fields¶

    Ideally, the authenticated data should include more than just the command.

    For example:

    Device ID
Resource path
Command
Sequence number
Protocol/context identifier

    This prevents an attacker from reusing an authentication tag in a different context.

    You should also use constant-time HMAC comparison and secure key storage.

    20.8 The packet sniffer is specific to your topology¶

    Your sniffer works because all nodes share the same CSMA channel.

    In a real switched Ethernet network, an ordinary host generally cannot see unicast traffic between two other hosts without mechanisms such as:

    • Switch port mirroring.
    • A network TAP.
    • Compromised network infrastructure.
    • An appropriate network interception position.

    This is a useful distinction if your faculty asks whether the same attack works on every LAN.

    22. Likely viva questions and answers¶

    Here are the questions I'd prioritize.

    Q1. Why did you choose CoAP instead of MQTT?¶

    CoAP is a lightweight application-layer protocol designed for constrained IoT devices. It supports resource-oriented communication using methods such as GET, POST, PUT, and DELETE.

    Unlike MQTT, which follows a broker-based publish-subscribe model, CoAP uses a client-server request-response model.

    It also supports Confirmable messages with acknowledgement and retransmission mechanisms.

    Q2. Why does CoAP use UDP?¶

    UDP has lower communication overhead and doesn't require connection establishment.

    This makes it suitable for constrained IoT devices.

    However, UDP doesn't guarantee delivery, so CoAP provides its own reliability mechanism for Confirmable messages.

    Q3. What is the difference between CON and NON?¶

    CON requires acknowledgement and supports retransmission.

    NON doesn't require acknowledgement and is suitable for periodic sensor readings where occasional loss is acceptable.

    Q4. Does CoAP provide security?¶

    CoAP itself doesn't automatically provide authentication or encryption.

    Security can be implemented using:

    • DTLS for securing CoAP over UDP.
    • OSCORE for end-to-end protection of CoAP messages.
    • Application-level authentication mechanisms such as HMAC.

    Q5. What is HMAC?¶

    HMAC is a message authentication mechanism based on a cryptographic hash function and a shared secret key.

    It provides message integrity and authentication.

    It allows the receiver to verify that the message was generated by someone possessing the shared secret and wasn't modified.

    Q6. Does HMAC prevent replay attacks?¶

    No.

    An attacker can capture a valid message along with its valid HMAC and retransmit it.

    HMAC will still verify successfully.

    We need sequence numbers, nonces, timestamps, or other freshness mechanisms to prevent replay attacks.

    Q7. Why do you need IP spoofing if you already have direct command injection?¶

    Direct injection sends a packet using the attacker's actual IP address.

    If the Cooler accepts commands only from the PLC IP, direct injection will be rejected.

    IP spoofing attempts to bypass this particular defense by forging the source IP address.

    It demonstrates why trusting source IP addresses alone isn't sufficient.

    Q8. Why do you use a raw socket?¶

    A normal UDP socket relies on the network stack to construct the IP header.

    I need to construct a packet with a forged source IP address.

    Therefore, I use an IPv4 raw socket and enable IpHeaderInclude so that the manually constructed IPv4 header is used.

    Q9. What is promiscuous mode?¶

    Promiscuous mode allows a network interface to receive packets that aren't addressed to its own MAC address and deliver them to a packet-capture mechanism.

    I use this to observe communication between the PLC and Cooler.

    Q10. Why do you copy the packet before removing headers?¶

    Because I only want to inspect the packet.

    I don't want to modify the original packet being processed by ns-3.

    Therefore, I create a copy and remove IPv4 and UDP headers from that copy.

    Q11. Why do you store the original CoAP bytes?¶

    I need to replay the exact original authenticated message.

    Storing the serialized bytes preserves the Message ID, Token, resource path, payload, sequence number, and HMAC.

    Q12. Why does replay protection use sequence numbers?¶

    A sequence number helps identify whether a command is newer than previously accepted commands.

    If the Cooler has already accepted sequence number 42, it can reject another command carrying sequence number 42.

    Q13. Why isn't a UDP checksum sufficient for authentication?¶

    A UDP checksum detects accidental transmission errors.

    It doesn't prove who generated the packet.

    An attacker can construct a malicious packet and calculate a valid UDP checksum.

    HMAC provides cryptographic message authentication.

    Q14. What is the difference between authentication and authorization?¶

    Authentication establishes who the sender is.

    Authorization determines whether that sender is allowed to perform a particular operation.

    For example:

    • Authentication: Is this really the PLC?
    • Authorization: Is this PLC allowed to turn off the cooler?

    Both are necessary.

    Q15. What happens if an attacker modifies the temperature reading?¶

    The PLC might receive incorrect measurements and make incorrect control decisions.

    A secure system should authenticate sensor messages and validate their values before using them in control logic.

    Q16. How is your project related to STUXNET?¶

    STUXNET demonstrated how cyberattacks could manipulate industrial control systems and affect physical processes.

    My project simulates a PLC-based industrial environment and demonstrates how unauthorized commands, IP spoofing, invalid authentication, and replay attacks could interfere with actuator control.

    It is a simplified educational model of industrial cybersecurity threats, not a reproduction of STUXNET.
