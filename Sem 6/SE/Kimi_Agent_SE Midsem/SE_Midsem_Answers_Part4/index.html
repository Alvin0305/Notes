    Software Engineering - Midsem Exam Answers (Part 4)¶

    14. RELATIONSHIPS - ANSWERS¶

    Short Answer Questions¶

    Q1. What is an association in UML? How is it represented?

    Answer: An association is a relationship between classes showing that objects of one class are connected to objects of another.

    Representation: - Solid line between classes - Can have name - Can have direction arrow - Can have multiplicity

    Q2. What is multiplicity? List the common multiplicity values and their meanings.

    Answer: Multiplicity specifies how many instances of one class can be associated with instances of another.

    Common values:

    Notation Meaning
    1 Exactly one
    0..1 Zero or one
    * Zero or more
    1..* One or more
    n Exactly n
    n..m Between n and m

    Q3. What is the difference between unidirectional and bidirectional associations?

    Answer:

    Unidirectional Bidirectional
    Only one class knows about the other Both classes know about each other
    Arrow points to known class No arrow
    Lower coupling Higher coupling
    Example: Person -> Car Example: Person -- Car

    Q4. What is an association class? When is it needed?

    Answer: An association class is a class that is also an association.

    Needed when: - The association itself has attributes - The association has operations - The association has its own identity

    Example: - Employee works for Company - The "works for" association has attributes: salary, startDate

    Q5. What is aggregation? How is it different from a regular association?

    Answer: Aggregation is a "whole-part" relationship where the part can exist independently of the whole.

    Difference from association:

    Association Aggregation
    "knows a" "has a"
    No ownership Weak ownership
    Parts independent Parts can exist alone
    Hollow diamond Hollow diamond on whole side

    Example: - University has Departments - If University closes, Departments may still exist

    Q6. What is composition? How is it different from aggregation?

    Answer: Composition is a strong "whole-part" relationship where the part cannot exist without the whole.

    Difference from aggregation:

    Aggregation Composition
    Weak ownership Strong ownership
    Parts can exist alone Parts cannot exist alone
    Hollow diamond Filled diamond
    "has a" "contains a"

    Example: - House has Rooms - If House destroyed, Rooms are destroyed too

    Q7. What is generalization? How is it represented in UML?

    Answer: Generalization is an "is-a" relationship where a subclass inherits from a superclass.

    Representation: - Hollow triangle arrow pointing to superclass - Subclass at arrow tail

    Example:

          Vehicle
        ^
       /|
      / |
    Car  Truck

    Q8. What is the difference between generalization and inheritance?

    Answer:

    Generalization Inheritance
    UML concept Programming concept
    Relationship between classes Mechanism to reuse code
    "Is-a" relationship Implementation technique
    Modeling concept Language feature

    Generalization is the model; inheritance is the implementation.

    Q9. What is a dependency relationship? When is it used?

    Answer: A dependency is a weaker relationship where one class uses another.

    Used when: - One class temporarily uses another - Parameter type - Local variable - Return type

    Representation: - Dashed arrow

    Example:

    Controller - - - > Service

    Q10. What is a realization relationship? Give an example.

    Answer: Realization is a relationship between a specification (interface) and its implementation.

    Example:

          <<interface>>
      PaymentProcessor
            ^
            |
       +----+----+
   PayPal    CreditCard

    PayPal and CreditCard realize (implement) PaymentProcessor interface.

    Long Answer Questions¶

    Q11. Compare and contrast association, aggregation, and composition. Give examples of each and explain when to use them.

    Answer:

    Aspect Association Aggregation Composition
    Relationship "knows a" "has a" "contains a"
    Strength Weak Medium Strong
    Ownership None Weak Strong
    Lifetime Independent Part can exist alone Part dies with whole
    UML Line Hollow diamond Filled diamond

    Examples:

    Association:

    Professor --- teaches --- Course

    Professor knows about Course, no ownership.

    Aggregation:

    University <>--- Department

    University has Departments, but Departments can exist independently.

    Composition:

    House <*>--- Room

    House contains Rooms; Rooms cannot exist without House.

    When to use: - Association: Simple relationship, no ownership - Aggregation: Whole-part, parts reusable - Composition: Whole-part, parts not reusable

    Q12. Explain the concept of multiplicity in detail. How do you determine the appropriate multiplicity for a relationship?

    Answer: Multiplicity defines how many instances participate in a relationship.

    Determining multiplicity:

    1. Analyze business rules:
    2. "A customer can have multiple orders" -> 1..*

    3. "An order belongs to exactly one customer" -> 1

    4. Consider real-world constraints:

    5. Physical limitations

    6. Business policies

    7. Ask questions:

    8. Can there be zero?
    9. Is there a maximum?

    10. Is there a minimum?

    11. Examples:

    12. Person -- Address: 1..* (person has at least one address)
    13. Order -- OrderLine: 1..* (order has at least one line)
    14. Employee -- Manager: 0..1 (employee may or may not have manager)

    Q13. Describe the different types of relationships that can exist between classes in UML. For each, explain its semantics and notation.

    Answer:

    1. Association:
    2. Semantics: "knows a"

    3. Notation: Solid line

    4. Directed Association:

    5. Semantics: One-way knowledge

    6. Notation: Solid line with arrow

    7. Aggregation:

    8. Semantics: "has a" (weak)

    9. Notation: Hollow diamond on whole

    10. Composition:

    11. Semantics: "contains a" (strong)

    12. Notation: Filled diamond on whole

    13. Generalization:

    14. Semantics: "is a"

    15. Notation: Hollow triangle arrow

    16. Dependency:

    17. Semantics: "uses"

    18. Notation: Dashed arrow

    19. Realization:

    20. Semantics: "implements"
    21. Notation: Dashed arrow with hollow triangle

    Q14. Explain the concept of navigability in associations. What are the implications of navigability for implementation?

    Answer: Navigability indicates whether one class can access another through the association.

    Representation: - Arrow shows direction of navigation - No arrow = bidirectional

    Implications for implementation:

    Navigability Implementation
    Unidirectional Reference in one class only
    Bidirectional References in both classes

    Example:

    Order -----> OrderLine
    • Order has reference to OrderLine
    • OrderLine doesn't know about Order
    • Lower coupling

    15. DESIGN PATTERNS - ANSWERS¶

    Short Answer Questions¶

    General Design Patterns¶

    Q1. What is a design pattern? What are the three main categories of design patterns?

    Answer: A design pattern is a reusable solution to a commonly occurring problem in software design.

    Three categories (GoF): 1. Creational: Object creation mechanisms 2. Structural: Class and object composition 3. Behavioral: Communication between objects

    Q2. What are the benefits of using design patterns?

    Answer: 1. Proven solutions: Tested and validated 2. Reusability: Apply same solution to similar problems 3. Communication: Common vocabulary 4. Maintainability: Well-structured code 5. Reduced complexity: Elegant solutions 6. Best practices: Follow good design principles

    Q3. What is the difference between a design pattern and a framework?

    Answer:

    Design Pattern Framework
    Abstract solution Concrete implementation
    Language-independent Language-specific
    Reusable idea Reusable code
    Smaller scope Larger scope
    Example: Singleton Example: Spring Framework

    Facade Pattern¶

    Q4. What is the Facade pattern? What problem does it solve?

    Answer: The Facade pattern provides a simplified interface to a complex subsystem.

    Problem it solves: - Complex subsystem with many classes - Client code becomes complex when using subsystem directly - Tight coupling between client and subsystem

    Solution: - Single entry point (facade) - Simplified interface - Reduced coupling

    Q5. What is the intent of the Facade pattern?

    Answer: Intent (GoF): "Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use."

    Q6. Give an example scenario where the Facade pattern would be useful.

    Answer: Scenario: A home theater system with multiple components: - Amplifier - DVD Player - Projector - Screen - Lights

    Without Facade: Client must interact with each component separately.

    With Facade:

    HomeTheaterFacade theater = new HomeTheaterFacade(amp, dvd, projector, screen, lights);
theater.watchMovie("Inception"); // Simplified!

    Q7. How does the Facade pattern reduce coupling?

    Answer: - Client depends only on Facade, not on subsystem classes - Subsystem can change without affecting client - Facade encapsulates subsystem complexity - Single point of contact

    Observer Pattern¶

    Q8. What is the Observer pattern? What problem does it solve?

    Answer: The Observer pattern defines a one-to-many dependency between objects.

    Problem it solves: - One object (subject) changes state - Multiple objects (observers) need to be notified - Tight coupling if subject knows all observers directly

    Solution: - Subject maintains list of observers - Observers register themselves - Subject notifies all observers when state changes

    Q9. What are the main components of the Observer pattern?

    Answer: 1. Subject: - Knows its observers - Provides interface for attaching/detaching observers

    1. Observer:

    2. Interface for objects that should be notified

    3. ConcreteSubject:

    4. Stores state

    5. Sends notification when state changes

    6. ConcreteObserver:

    7. Maintains reference to ConcreteSubject
    8. Implements update interface

    Q10. Give a real-world example of the Observer pattern.

    Answer: Newsletter subscription: - Publisher (Subject) sends newsletters - Subscribers (Observers) receive newsletters - Subscribers can subscribe/unsubscribe - When new newsletter published, all subscribers notified

    Stock price monitoring: - Stock (Subject) price changes - Multiple displays (Observers) show updated price - New displays can be added without changing Stock class

    Q11. How does the Observer pattern reduce coupling?

    Answer: - Subject doesn't know concrete observers - Only knows Observer interface - Observers can be added/removed dynamically - Subject and observers can vary independently - Supports open/closed principle

    Q12. What is the difference between push and pull models in the Observer pattern?

    Answer:

    Push Model Pull Model
    Subject sends data to observers Observers request data from subject
    update(data) update()
    Observers receive all data Observers get only what they need
    Less flexible More flexible
    Simpler for observers More efficient

    Adapter Pattern¶

    Q13. What is the Adapter pattern? What problem does it solve?

    Answer: The Adapter pattern converts the interface of a class into another interface that clients expect.

    Problem it solves: - Incompatible interfaces - Want to use existing class but interface doesn't match - Can't modify existing class (legacy, third-party)

    Solution: - Create adapter that wraps existing class - Adapter implements target interface - Client uses adapter, adapter delegates to adaptee

    Q14. What are the two types of Adapter pattern? Explain each.

    Answer:

    1. Object Adapter:
    2. Uses composition
    3. Adapter holds reference to adaptee

    4. More flexible (can adapt subclasses)

    5. Class Adapter:

    6. Uses inheritance
    7. Adapter inherits from adaptee
    8. Less flexible (requires multiple inheritance in some languages)

    Q15. Give an example scenario where the Adapter pattern would be useful.

    Answer: Scenario: Integrating a legacy payment system with new e-commerce application.

    Legacy system:

    class LegacyPayment {
    void makePayment(double amount) { ... }
}

    New system expects:

    interface PaymentProcessor {
    void processPayment(BigDecimal amount);
}

    Adapter:

    class PaymentAdapter implements PaymentProcessor {
    private LegacyPayment legacy;

    void processPayment(BigDecimal amount) {
        legacy.makePayment(amount.doubleValue());
    }
}

    Q16. How does the Adapter pattern improve reuse and flexibility?

    Answer: - Allows reuse of existing classes with incompatible interfaces - No need to modify existing code - Can adapt multiple classes to same interface - Client code uses standard interface - Easy to swap implementations - Supports open/closed principle

    Long Answer Questions¶

    Q17. Describe the Facade pattern in detail.

    Answer: Intent: Provide a unified interface to a set of interfaces in a subsystem.

    When to use: - Simplify complex subsystem - Layer system - Decouple subsystems

    Structure:

    +----------+
|  Client  |
+-----+----+
      | uses
      v
+----------+
|  Facade  |<-----------+
+-----+----+            |
      | knows           |
      v                 |
+----------+  +----------+  +----------+
|SubsystemA|  |SubsystemB|  |SubsystemC|
+----------+  +----------+  +----------+

    Participants: - Facade: Knows subsystem responsibilities, delegates requests - Subsystem classes: Implement functionality, handle work

    Benefits: - Shields clients from subsystem complexity - Promotes weak coupling - Doesn't prevent direct subsystem access

    Drawbacks: - Facade can become a "god object" - May limit flexibility if overused

    Q18. Describe the Observer pattern in detail.

    Answer: Intent: Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

    When to use: - One object changes, others need to know - Don't know how many objects need to change - Objects should be loosely coupled

    Structure:

    +-----------------+         +-------------+
|  <<interface>>  |         |  <<interface|
|    Subject      |<--------|   Observer  |
+-----------------+         +-------------+
| attach(Observer)|         |   update()  |
|detach(Observer) |         +------+------+
|    notify()     |                |
+--------+--------+                |
         | implements               | implements
         v                          v
+-----------------+         +-------------+
| ConcreteSubject |         |ConcreteObserver
+-----------------+         +-------------+
|   getState()    |-------->|   update()  |
|   setState()    |         |             |
+-----------------+         +-------------+

    Participants: - Subject: Knows observers, provides attach/detach interface - Observer: Interface for notification - ConcreteSubject: Stores state, notifies observers - ConcreteObserver: Maintains reference, implements update

    Benefits: - Abstract coupling between Subject and Observer - Support for broadcast communication - Observers can be added/removed dynamically

    Drawbacks: - Unexpected updates - Memory leaks if observers not detached - Update order dependencies

    Q19. Describe the Adapter pattern in detail.

    Answer: Intent: Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.

    When to use: - Use existing class with incompatible interface - Create reusable class that cooperates with unforeseen classes - Use several existing subclasses, but adapting their interface is impractical

    Structure (Object Adapter):

    +----------+
|  Client  |
+-----+----+
      | uses
      v
+----------+
|  Target  |<-----------+
| interface|            |
+-----+----+            |
      | implements      |
      v                 |
+----------+            |
|  Adapter |------------+
+----------+
      | uses
      v
+----------+
|  Adaptee |
|specific  |
|Request() |
+----------+

    Participants: - Target: Interface client expects - Adapter: Adapts Adaptee to Target interface - Adaptee: Existing interface to be adapted - Client: Uses Target interface

    Benefits: - Reuse existing classes - Add flexibility - No modification to adaptee

    Drawbacks: - Additional complexity - May need multiple adapters

    Q20. Compare and contrast the Facade, Observer, and Adapter patterns.

    Answer:

    Aspect Facade Observer Adapter
    Category Structural Behavioral Structural
    Purpose Simplify interface Notify changes Convert interface
    Problem Complex subsystem State change notification Incompatible interfaces
    Solution Unified interface Subscription mechanism Interface translation
    Coupling Reduces Reduces Reduces
    Flexibility Hides complexity Dynamic registration Enables reuse

    When to use: - Facade: Complex subsystem needs simple interface - Observer: One-to-many notification needed - Adapter: Need to use class with incompatible interface

    Q21. Explain how design patterns promote good software design principles such as low coupling and high cohesion.

    Answer:

    Low Coupling: - Facade: Client depends only on Facade, not subsystem - Observer: Subject only knows Observer interface - Adapter: Client depends on Target, not Adaptee

    High Cohesion: - Facade: Each subsystem class has single responsibility - Observer: Subject manages state, Observer handles notification - Adapter: Adapter only handles interface translation

    Other principles: - Open/Closed: Add new observers/adapters without changing existing code - Single Responsibility: Each pattern component has one job - Dependency Inversion: Depend on abstractions

    Q23. Discuss how the Observer pattern is used in the Model-View-Controller (MVC) architecture.

    Answer: MVC and Observer:

    +-------------------------------------+
|              Model                  |
|         (ConcreteSubject)           |
|         - Business logic            |
|         - Application state         |
+--------------+----------------------+
               | notify
        +------+------+
        |             |
        v             v
+-----------+   +-----------+
|    View   |   | Controller|
| (Concrete |   |           |
|  Observer)|   |           |
| - Display |   | - Input   |
|   data    |   |   handling|
+-----------+   +-----------+

    How it works: 1. Model contains data and business logic 2. Views register as observers of Model 3. When Model changes, it notifies all Views 4. Views update their display 5. Controllers handle user input and update Model

    Benefits: - Multiple views of same data - Automatic synchronization - Loose coupling

    Q24. Explain how the Adapter pattern can be used to integrate legacy code with new systems.

    Answer: Scenario: New system needs functionality from legacy system, but interfaces are incompatible.

    Solution: 1. Define interface expected by new system (Target) 2. Create Adapter that implements Target 3. Adapter wraps legacy system (Adaptee) 4. Adapter translates Target calls to Adaptee calls

    Example:

    // New system expects this interface
interface ModernPayment {
    void processPayment(PaymentDetails details);
}

// Legacy system has this interface
class LegacyPayment {
    void makePayment(double amount, String currency) { ... }
}

// Adapter bridges the gap
class PaymentAdapter implements ModernPayment {
    private LegacyPayment legacy;

    void processPayment(PaymentDetails details) {
        legacy.makePayment(
            details.getAmount(), 
            details.getCurrency()
        );
    }
}

    Benefits: - No changes to legacy code - New system uses standard interface - Easy to replace legacy system later - Can add functionality in adapter

    BONUS: COMPREHENSIVE QUESTIONS - ANSWERS¶

    Q1. You are asked to develop a new online banking system. Describe your approach.

    Answer: Feasibility Study: - Technical: Assess security requirements, technology stack - Economic: Cost-benefit analysis, ROI calculation - Schedule: Determine realistic timeline

    Process Model: - Choose Iterative/Agile approach - Banking requirements change frequently - Need early delivery of core features - Regulatory requirements need documentation

    Requirements Gathering: - Interview bank staff and customers - Analyze existing systems - Create use cases: Transfer Funds, Pay Bills, View Statements - Define security and performance requirements

    UML Diagrams: - Use case diagram: Show all banking functions - Class diagram: Account, Customer, Transaction classes - Sequence diagram: Fund transfer process - Activity diagram: Loan approval workflow - State diagram: Account states (Active, Frozen, Closed)

    Design Patterns: - Facade: Simplify complex banking operations - Observer: Notify customers of transactions - Adapter: Integrate with legacy banking systems - Singleton: Database connection pool

    Q2. Compare and contrast all the process models.

    Answer: (See detailed comparison in Q16 of Process Models section)

    Q3. Explain the complete process of requirements engineering.

    Answer: Requirements Engineering Process:
