    Software Engineering - Midsem Exam Answers (Part 2)¶

    6. REQUIREMENT ANALYSIS - ANSWERS¶

    Short Answer Questions¶

    Q1. What is requirement analysis? Why is it important?

    Answer: Requirement analysis is the process of understanding, documenting, and validating what the customer needs from the software system.

    Importance: - Foundation for all subsequent development activities - Ensures the right system is built - Reduces risk of project failure - Provides basis for testing - Helps manage scope - Enables accurate cost and schedule estimation - Poor requirements are a leading cause of project failure

    Q2. List four techniques for gathering requirements.

    Answer: 1. Interviews - One-on-one discussions with stakeholders 2. Brainstorming - Group sessions to generate ideas 3. Use case analysis - Understanding user interactions 4. Prototyping - Creating mock-ups for feedback 5. Observation - Watching users work 6. Questionnaires - Surveys for large groups 7. Document analysis - Studying existing documentation

    Q3. What is domain analysis? Why should it be performed before gathering requirements?

    Answer: Domain analysis is the study of the business domain to understand terminology, processes, and existing systems.

    Why perform first: - Ensures effective communication with stakeholders - Prevents misunderstandings - Helps ask better questions - Understands existing solutions - Identifies constraints - Builds credibility with domain experts - Avoids reinventing the wheel

    Q4. What is the difference between functional and non-functional requirements? Give two examples of each.

    Answer:

    Functional Requirements Non-Functional Requirements
    Describe WHAT the system should do Describe HOW the system should behave
    Define specific behaviors Define quality attributes

    Examples of functional requirements: 1. The system shall allow users to search for products by name 2. The system shall send an email confirmation after order placement

    Examples of non-functional requirements: 1. The system shall respond to user queries within 2 seconds 2. The system shall be available 99.9% of the time

    Q5. What are quality requirements? Give three examples.

    Answer: Quality requirements (also called non-functional requirements) specify the quality attributes the system must have.

    Examples: 1. Performance: System shall process 100 transactions per second 2. Reliability: System shall have 99.9% uptime 3. Usability: New users shall learn the system within 2 hours 4. Security: All data shall be encrypted 5. Maintainability: Code shall have cyclomatic complexity less than 10

    Q6. What is the difference between a feature and a requirement?

    Answer:

    Feature Requirement
    High-level capability Detailed specification
    "The system shall have online payment" "The system shall process credit card payments through Visa and MasterCard"
    Often marketing-oriented Technical specification
    May include multiple requirements Single, verifiable statement

    Q7. What is gold-plating? Why should it be avoided?

    Answer: Gold-plating is adding features that are not necessary to solve the customer's problem.

    Why avoid it: - Increases cost without adding value - Extends schedule - Adds complexity - Increases maintenance burden - May introduce defects - Diverts resources from important features - Principle: "Build only what is needed"

    Long Answer Questions¶

    Q8. Describe the process of requirements gathering. What techniques can be used and when is each most appropriate?

    Answer: Process: 1. Identify stakeholders 2. Understand the domain 3. Select appropriate techniques 4. Gather information 5. Document findings 6. Validate with stakeholders 7. Iterate as needed

    Techniques and when to use:

    Technique When to Use
    Interviews Small number of key stakeholders; detailed understanding needed
    Brainstorming Early stage; generating ideas; creative solutions
    Use case analysis Understanding user interactions; functional requirements
    Prototyping Requirements unclear; UI design; getting user feedback
    Observation Users can't articulate needs; understanding actual work
    Questionnaires Large user groups; quantitative data needed
    Document analysis Existing systems; regulatory requirements

    Q9. Explain the principles for gathering good requirements as discussed in the textbook.

    Answer: 1. Perform domain analysis - Know enough to communicate effectively 2. Keep scope narrow - Focus on the real problem 3. Keep system general - Find higher-level goals 4. Gather all types - Functional, quality, platform, process 5. Combine techniques - Use multiple approaches for best results 6. Involve users - They know their needs best 7. Iterate - Requirements evolve 8. Document clearly - Unambiguous, verifiable 9. Validate - Get stakeholder agreement 10. Prioritize - Not all requirements are equal

    Q10. Discuss the different types of requirements (functional, quality, platform, process). Why is it important to distinguish between them?

    Answer: Types:

    1. Functional requirements:
    2. What the system should do
    3. Specific behaviors and functions

    4. Example: "System shall calculate tax"

    5. Quality requirements:

    6. How well the system should perform
    7. Performance, reliability, usability, security

    8. Example: "Response time shall be < 2 seconds"

    9. Platform requirements:

    10. Constraints on the environment
    11. Hardware, software, network

    12. Example: "System shall run on Windows 10"

    13. Process requirements:

    14. How the development should proceed
    15. Standards, methodologies, documentation
    16. Example: "Code shall follow Java coding standards"

    Why distinguish: - Different stakeholders care about different types - Different validation methods - Different impact on architecture - Helps prioritize - Ensures complete coverage

    Q11. What are the common problems in requirements gathering? How can they be addressed?

    Answer: Common problems:

    1. Incomplete requirements:

    2. Solution: Use multiple techniques, involve all stakeholders

    3. Ambiguous requirements:

    4. Solution: Use precise language, examples, prototypes

    5. Conflicting requirements:

    6. Solution: Facilitate discussions, prioritize, find compromises

    7. Changing requirements:

    8. Solution: Expect change, use iterative approach, change control process

    9. Users don't know what they want:

    10. Solution: Prototyping, observation, iterative refinement

    11. Communication gaps:

    12. Solution: Domain analysis, common terminology, visual models

    13. Gold-plating:

    14. Solution: Focus on real problems, cost-benefit analysis

    Q12. Explain the concept of scope creep. How can it be prevented or managed?

    Answer: Scope creep is the uncontrolled expansion of project scope after the project has started.

    Causes: - Poor initial requirements - Pressure from stakeholders - Lack of change control - "Just one more feature" mentality

    Prevention/Management: 1. Clear initial scope: Well-defined requirements 2. Change control process: Formal process for evaluating changes 3. Prioritization: Focus on must-haves first 4. Stakeholder agreement: Everyone agrees on scope 5. Regular reviews: Monitor for scope changes 6. Impact analysis: Assess cost of each change 7. Communication: Keep stakeholders informed 8. Iterative delivery: Deliver in increments

    7. SOFTWARE REQUIREMENTS SPECIFICATION (SRS) - ANSWERS¶

    Short Answer Questions¶

    Q1. What is an SRS document? What is its purpose?

    Answer: An SRS (Software Requirements Specification) document is a formal document that describes what the software system will do.

    Purpose: - Communicate requirements to all stakeholders - Basis for design and implementation - Foundation for testing - Reference for acceptance - Contract between customer and developer - Helps manage scope

    Q2. List five characteristics of a good requirement (the "quality criteria" for requirements).

    Answer: 1. Correct: Accurately describes needed functionality 2. Unambiguous: Only one interpretation 3. Complete: All necessary information included 4. Consistent: No conflicts with other requirements 5. Verifiable: Can be tested or inspected 6. Traceable: Can be traced to origin and implementation 7. Prioritized: Importance is indicated 8. Modifiable: Easy to change

    Q3. What does it mean for a requirement to be verifiable? Give an example of a requirement that is NOT verifiable.

    Answer: A requirement is verifiable if there is a finite, cost-effective way to check that it has been met.

    Verifiable example: - "The system shall display search results within 3 seconds" - Can be tested by timing searches

    NOT verifiable example: - "The system shall be user-friendly" - Too subjective; no clear way to verify

    Better version: - "New users shall complete a task within 5 minutes with no more than 2 errors"

    Q4. What is traceability in the context of requirements?

    Answer: Traceability is the ability to track a requirement from its origin through implementation and testing.

    Types: - Forward: Requirements → Design → Code → Tests - Backward: Tests → Code → Design → Requirements

    Benefits: - Impact analysis for changes - Verification of completeness - Testing coverage - Maintenance support

    Q5. What is a use case? How does it relate to requirements?

    Answer: A use case describes a sequence of actions a system performs to yield an observable result of value to an actor.

    Relationship to requirements: - Use cases capture functional requirements - Each use case represents a requirement or set of requirements - Use cases describe system behavior from user perspective - Help validate requirements with users - Provide basis for test cases

    Long Answer Questions¶

    Q6. Describe the typical contents of an SRS document. What sections should it contain?

    Answer: Typical SRS contents:

    1. Introduction
    2. Purpose
    3. Scope
    4. Definitions and acronyms

    5. References

    6. Overall Description

    7. Product perspective
    8. Product functions
    9. User characteristics
    10. Constraints

    11. Assumptions and dependencies

    12. Specific Requirements

    13. Functional requirements
    14. External interface requirements
    15. Performance requirements
    16. Design constraints
    17. Quality attributes

    18. Other requirements

    19. Appendices

    20. Supporting information
    21. Use cases
    22. Glossary

    Q7. Explain the principles for writing good requirements documents as discussed in the textbook.

    Answer: 1. Ensure benefit outweighs cost - Each requirement should add value 2. Contribute to problem solution - Must address a real need 3. Express clearly and consistently - Use clear language 4. Be unambiguous - Only one interpretation 5. Be consistent - No conflicts 6. Contribute to sufficient quality - Meet quality standards 7. Be developable with available resources - Feasible 8. Be verifiable - Can be tested 9. Be uniquely identifiable - Each has unique ID 10. Not over-constrain design - Allow design flexibility 11. Be sufficiently complete - Cover all needs 12. Organize effectively - Logical structure 13. Give clear rationale - Explain why 14. Obtain stakeholder agreement - Everyone agrees

    Q8. What is the difference between user requirements and system requirements? How are they documented differently?

    Answer:

    User Requirements System Requirements
    Written for users/customers Written for developers
    High-level, in user language Detailed, technical
    Describe what users need Describe what system does
    Less formal More formal
    May use natural language May use formal notations

    Documentation: - User requirements: In language users understand, focus on business value - System requirements: Precise, technical, may include models and specifications

    Q9. Discuss the importance of requirements review. What should be checked during a requirements review?

    Answer: Importance: - Catch errors early (cheaper to fix) - Ensure completeness - Get stakeholder agreement - Improve quality - Reduce risk

    What to check: 1. Correctness - Does it match user needs? 2. Completeness - Is anything missing? 3. Consistency - Any conflicts? 4. Clarity - Is it understandable? 5. Verifiability - Can it be tested? 6. Traceability - Can it be traced? 7. Feasibility - Can it be implemented? 8. Priority - Is importance indicated? 9. Ambiguity - Any unclear statements? 10. Redundancy - Any duplication?

    Q10. Explain how requirements should be organized in an SRS document for maximum clarity and usability.

    Answer: Organization principles:

    1. Logical grouping:
    2. Group by feature
    3. Group by user type

    4. Group by subsystem

    5. Hierarchical structure:

    6. High-level requirements first

    7. Detailed requirements follow

    8. Unique identification:

    9. Each requirement has unique ID

    10. Enables traceability

    11. Consistent format:

    12. Same template for all requirements

    13. Includes ID, description, priority, rationale

    14. Cross-references:

    15. Link related requirements

    16. Link to use cases

    17. Index and glossary:

    18. Easy to find requirements
    19. Common terms defined

    8. REQUIREMENT MODELING - ANSWERS¶

    Short Answer Questions¶

    Q1. What is requirement modeling? Why is it important?

    Answer: Requirement modeling is the creation of abstract representations (models) of the system to understand and communicate requirements.

    Importance: - Visual communication - Abstraction from details - Identify gaps and inconsistencies - Basis for design - Validate understanding - Common understanding among stakeholders

    Q2. List three types of models that can be used for requirement modeling.

    Answer: 1. Use case models - Show system functionality from user perspective 2. Domain models (class diagrams) - Show concepts and relationships 3. Activity diagrams - Show business processes 4. State diagrams - Show object lifecycle 5. Sequence diagrams - Show interactions

    Q3. What is the purpose of a domain model?

    Answer: A domain model shows: - Key concepts (classes) in the problem domain - Relationships between concepts - Attributes of concepts

    Purpose: - Understand the domain - Common vocabulary - Foundation for design - Communication with domain experts - Identify key abstractions

    Q4. What is the difference between analysis and design in the context of modeling?

    Answer:

    Analysis Design
    Focus on WHAT Focus on HOW
    Understand requirements Plan implementation
    Domain-oriented Solution-oriented
    Technology-independent Technology-specific
    "What should the system do?" "How will the system do it?"

    Q5. What is OCL (Object Constraint Language)? What is it used for?

    Answer: OCL is a formal language for expressing constraints and queries on UML models.

    Used for: - Specifying invariants (conditions that must always be true) - Pre and post conditions - Guard conditions - Derivation rules - Query expressions

    Example:

    context Employee inv:
  self.age >= 18

    Long Answer Questions¶

    Q6. Describe how UML can be used for requirement modeling. What diagrams are most useful at this stage?

    Answer: UML for requirement modeling:

    1. Use case diagrams:
    2. Capture functional requirements
    3. Show system scope

    4. Identify actors

    5. Activity diagrams:

    6. Model business processes
    7. Show workflow

    8. Identify system boundaries

    9. Domain class diagrams:

    10. Identify key concepts
    11. Show relationships

    12. Build common vocabulary

    13. State diagrams:

    14. Model lifecycle of key objects

    15. Identify events and transitions

    16. Sequence diagrams:

    17. Show interactions for key scenarios
    18. Validate use cases

    Q7. Explain the process of creating a domain model. What elements should be included?

    Answer: Process: 1. Identify key concepts (nouns from requirements) 2. Identify attributes 3. Identify relationships 4. Determine multiplicities 5. Refine and validate

    Elements to include: - Classes: Key concepts (e.g., Customer, Order, Product) - Attributes: Properties of classes - Associations: Relationships between classes - Multiplicities: How many instances participate - Association classes: When relationship has attributes - Generalizations: "Is-a" relationships

    Q8. Discuss the relationship between requirements and models. How do models help in understanding and communicating requirements?

    Answer: Relationship: - Models are visual representations of requirements - Multiple models may represent same requirements - Models provide different perspectives

    How models help:

    1. Understanding:
    2. Abstraction removes details
    3. Visual representation easier to understand

    4. Different perspectives reveal different aspects

    5. Communication:

    6. Common visual language
    7. Bridge between technical and non-technical stakeholders

    8. Reduce ambiguity

    9. Validation:

    10. Stakeholders can review models
    11. Identify missing or incorrect requirements

    12. Early feedback

    13. Foundation for design:

    14. Models evolve into design
    15. Maintain traceability

    9. USE CASE DIAGRAM - ANSWERS¶

    Short Answer Questions¶

    Q1. What is a use case diagram? What does it show?

    Answer: A use case diagram is a UML behavioral diagram that shows: - System functionality (use cases) - Users/External systems (actors) that interact with the system - Relationships between use cases and actors

    It shows WHAT the system does from an external perspective.

    Q2. Draw the UML notation for various use case diagram elements.

    Answer:

    Actor:         Use Case:         <<include>>:
  |              ______              ______
 /|\            /      \            /      \
  |    -------->( Use    )    ----->( Included)
 / \            \ Case /            \______/
 Stick figure    \______/
                Oval

<<extend>>:      System Boundary:
  ______         +------------------+
 /      \       |                  |
( Extending)--->|  Use Case        |
 \______/       |                  |
                +------------------+
                Rectangle

    Q3. What is the difference between <\> and <\> relationships? Give an example of each.

    Answer:

    <\> <>
    Base use case always includes the included use case Extension use case adds behavior conditionally
    Mandatory Optional
    Arrow points to included use case Arrow points from extending to base

    <\> example: - "Place Order" includes "Verify Credit Card" - Verification always happens

    <\> example: - "Search Product" is extended by "Show Recommendations" - Recommendations shown only sometimes

    Q4. What is a generalized actor? How is it represented?

    Answer: A generalized actor is an actor that inherits from another actor.

    Representation: - Hollow triangle arrow pointing to parent actor - Child actor inherits parent's associations

    Example:

          User
        ^
       /|
      / |
  Customer  Administrator

    Both Customer and Administrator can do what User can do.

    Q5. What is a system boundary in a use case diagram?

    Answer: A system boundary is a rectangle that: - Encloses the use cases - Separates the system from external actors - Shows scope of the system - Named with the system name

    Q6. What are the guidelines for naming use cases?

    Answer: 1. Use verb-noun format (e.g., "Place Order", "Withdraw Cash") 2. Name from actor's perspective 3. Use active voice 4. Be specific and descriptive 5. Avoid technical jargon 6. Keep it concise 7. Use consistent terminology

    Long Answer Questions¶

    Q7. Describe the components of a use case diagram. Explain each component with examples.

    Answer: Components:

    1. Actors:
    2. External entities that interact with system
    3. Can be people, other systems, devices

    4. Example: Customer, Bank System

    5. Use Cases:

    6. System functionality
    7. Oval shape

    8. Example: "Place Order", "Check Balance"

    9. System Boundary:

    10. Rectangle enclosing use cases

    11. Shows system scope

    12. Associations:

    13. Lines connecting actors to use cases

    14. Show participation

    15. <\> relationship:

    16. One use case always includes another

    17. Arrow to included use case

    18. <\> relationship:

    19. One use case optionally extends another

    20. Arrow from extending to base

    21. Generalization:

    22. Actor or use case inheritance

    Q8. Explain how to identify actors for a system. What questions should you ask?

    Answer: Questions to identify actors:

    1. Who uses the system?
    2. Who installs the system?
    3. Who starts and shuts down the system?
    4. Who maintains the system?
    5. What other systems interact with this system?
    6. Who gets information from the system?
    7. Who provides information to the system?
    8. What happens at specific times?

    Types of actors: - Primary actors: Initiate use cases - Secondary actors: Participate but don't initiate - External systems: Other software systems

    Q9. What is the relationship between use cases and requirements? How do use cases help in requirements gathering?

    Answer: Relationship: - Use cases capture functional requirements - Each use case represents one or more requirements - Use cases organize requirements by user goal

    How use cases help:

    1. User-centric:
    2. Focus on what users want to achieve

    3. Easy for users to understand and validate

    4. Complete picture:

    5. Show all ways users interact with system

    6. Help identify missing requirements

    7. Communication:

    8. Common language between users and developers

    9. Visual representation

    10. Test basis:

    11. Use cases become test cases

    12. Ensure all functionality is tested

    13. Scope management:

    14. Clear boundaries
    15. Easy to identify gold-plating
